# M1 兩階段規則

兩階段是工作責任，不代表一定要兩次使用者操作。

## 階段一：弱電來源抽取

輸入：使用者上傳的 PDF。

程式分批擷取原生文字、表格、OCR、頁碼與上下文；所有可讀來源片段都要進入 AI 閱讀，既有詞表、分數與系統提示只可當提示，不可當納入門檻。AI 逐批判斷弱電業務相關性，疑似相關時預設保留。結果合併為 `weak_current_source.md`。

每個保留項目至少包含：

- PDF 頁碼。
- 章節或位置。
- 候選 ID。
- 來源原文。
- 理解需求所需的前後文。

本階段不得寫正式需求、決定最終系統、建立需求樹或使用封閉關鍵字排除未知設備。

所有來源閱讀批次都必須完成。每個結果須包含 screened、reviewed-pages、reviewed-groups 三個 marker，證明實際讀過批次指定的頁碼與群組。低信心 OCR 保留草稿，每個 pending 影像區都由模型針對裁切圖判為 read、unreadable 或 skipped_non_text；不要求把不可讀影像強行辨識成文字。未經模型判讀的 pending 不得合併；已判為不可讀或非文字者不阻斷全案，疑似與弱電相關且影響理解時列入來源待確認。

全部批次完成後，AI 讀取 manifest 的群組輪廓做一次文件級漏項複核。若發現表格、OCR、特殊空間、跨專業介面或整批零保留等異常，只重讀疑似漏項的批次並修正對應結果；不重新掃描 PDF，也不增加逐筆語意評分器。

完成合併時由程式同步建立 `stage1_receipt.json`，只記錄來源檔名與 SHA、PDF 頁數、抽取及篩選批次數、已完成批次 ID、已覆核頁碼與群組、證據群組數、保留候選數及 `weak_current_source.md` 雜湊。它只證明第一階段實際完成，不做工程語意判斷。

## 階段二：AI 轉譯與交付

輸入：`weak_current_source.md` 與其 `stage1_receipt.json`。第二階段開始前必須先核對來源包雜湊及批次覆蓋；不得臨時重建一份來源包或跳回 PDF 直接產生需求。

AI 依舊版方式：

1. 理解章節、表格、上下文、空間與責任。
2. 合併同一義務，拆分不同設備、空間、動作、條件、數量及確認狀態。
3. 建立自然、完整、可設計或查核的工程需求。
4. 建立系統、可讀主題、人工確認及摘要導讀。
5. 產生唯一 `requirements_master.md`。
6. 投影三份成果並封裝 ZIP。

程式只做來源與格式檢查，不得補寫需求、分類語意或修改 AI 文字。

## 輕量 Harness

只檢查：

- 每個來源閱讀批次都有 screened、reviewed-pages、reviewed-groups marker，且與 manifest 一致。
- `stage1_receipt.json` 與實際來源包的雜湊、來源檔、PDF 頁數及批次 ID 一致。
- 來源檔名與 SHA 一致。
- 每筆正式需求有頁碼及短原文。
- 三份交付的 ID、數量與需求文字一致。
- HTML 無占位符、重複 ID、直排文字或破版。

## 回合控制

預設兩階段在上傳回合連續完成。大型 PDF 可以在同一回合分批執行；只有平台真的中斷時，使用者輸入一次「繼續」才從現有批次檔接續。不得把純渲染拆成另一輪，也不得要求使用者輪詢假背景工作。

正式中間檔只有：

- `weak_current_source.md`：弱電來源包。
- `stage1_receipt.json`：第一階段完成與檔案一致性收據，不是交付成果。
- `requirements_master.md`：唯一語意主檔。
